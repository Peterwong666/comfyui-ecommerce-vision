## 1. 适用范围

**适用**：批量任务（`POST /api/v1/batches`）产出的成图。抽检单位是**单张子任务**
（`tasks` 表的一行）—— 这不是随意的选择：PRD §3.1 把子任务粒度定为"一张图"，
正是为了"失败能精确隔离、断点续跑只重跑失败的那几张"（`tasks.py:390-391`）。
判废必须落在同一粒度上，否则"判废一张"无法翻译成"重跑哪一条任务"。

**不适用**：
- 单任务提交（`POST /api/v1/tasks`）：只有 1 张，没有"抽"的余地，判读即全检。
- A/B 对比测试（P8-07）：目的是比较方案差异，不是批次质量门。
- golden set 回归（P8-08）：那是**变更门禁**，样本是固定的、跨批次不变的；抽检的
  样本是从**当批产物**里抽的。两者不能互相替代 —— golden set 通过不代表这一批
  产品图可用（提示词、素材、参数都不同）。

## 2. 抽样规则

### 2.1 抽样比例

| 批次张数 N | 抽样数 | 依据 |
|---|---|---|
| N ≥ 100 | `max(10, ceil(N × 10%))` | 需求原文「批量 ≥100 张抽检 10%」 |
| N < 100 | **全检 = N 张（100%）** | 见下方理由 |

**为什么 N < 100 是全检而不是"也抽 10%"**

1. **小样本的估计比没有估计更危险。** N=99 时 10% 只有 9 张；若其中 1 张判废，
   抽检良品率的点估计是 89%，但它对应的不确定性大到无法支撑任何决策
   （真实不良率可能是 1%，也可能是 20%）。一个**看起来像数**的错数，
   比"这一批我们逐张看过"更会误导排产。
2. **工作量有界。** N ≤ 99 时全检的判读量上限就是 99 张，是一天之内能完成的事；
   而 ≥100 张之后全检的边际成本随批次线性增长，才真正需要抽样。
3. **与交付视图重合。** 电商详情页/主图批量通常是几十张量级，
   这批图客户自己也会逐张看 —— 抽检和交付验收看的是同一批眼睛，没有重复成本。

⚠️ **取舍**：全检没有抽样误差，但也没有"抽检"这个概念的统计意义；
它的价值是**保证不漏**，代价是判读工时。若将来实测发现 60–99 张的全检经常拖期，
再引入"低风险批次按 30% 抽"的分级 —— 但在有真实工时数据之前**不要**先加这个复杂度。

⚠️ **10% 只规定了比例，没规定上限。** 一个 1000 张的批次按规则要判读 100 张，
这是**刻意的**：本 SOP 不允许用"抽检上限 50 张"之类的护栏去悄悄弱化需求里写死的比例。
若 100 张/批的人工成本不可接受，正确做法是走 §5 的分层并行（拆给多人），
而不是改比例。

### 2.2 抽样触发时机

抽检在**整批到达终态之后**做，不在运行中抽。判据：父批次不再有新产物落库
（子任务全部落在 `succeeded` / `failed` / `canceled`）。

理由：运行中抽样会抽到"还会被自动重试覆盖"的张（T7 → T8，`mark_retrying`），
那张图在抽检时看到的和最终交付的不是同一份产物 —— 判读结论会失效。
（⚠️ 前提提醒：`partial` 批次的"断点续跑"能力对应 `AC-F4`，目前**未验证**；
本 SOP 不假设它可用，续跑后的产物按 §2.2 重新触发一次抽检。）

### 2.3 抽样方法：**分层随机**，不是均匀随机

**分层维度（按优先级，取第一个在该批内存在 ≥2 个不同取值的维度）**
这是刻意的"只分一层"设计：维度叠加会让每层样本数掉到 1–2 张，
分层就从"提高覆盖"变成"制造噪声"。

| 优先级 | 分层键 | 为什么是它 |
|---|---|---|
| 1 | `workflow`（工作流） | **不同工作流的失效模式不同**（见下） |
| 2 | `model`（底模 / checkpoint hash） | 换底模等于换了一个生成分布，缺陷类型跟着换 |
| 3 | 分辨率档（如 512–1024 / 1024–1536 / 1537–2048） | 高分辨率常见边缘/纹理崩坏，低分辨率常见糊 |
| 4 | 参数档（steps 或 cfg 非默认值的张） | 非默认参数是"少数派但要重点看"的一类 |
| — | 不分层（均匀随机） | 仅当上述维度在本批内都只有单一取值时 |

**为什么不同工作流的失效模式确实不同**（不是泛泛而谈，是各条链路的结构差异）：
- `i2i_v1`：产物质量由**参考图一致性**决定（denoise 越低越贴原图），
  典型缺陷是"和参考图不像"，这在纯 t2i 里不存在。
- `inpaint_v1`：由**蒙版**决定重绘范围，典型缺陷是"改错了地方"或"没改"，
  这类缺陷在结构上与其他工作流正交。（⚠️ 该工作流的**蒙版极性至今没有实测结论**，
  见 `workflows/registry.yaml:339-345` 与 §7。）
- `upscale_v1`：由**细节重建**决定，典型缺陷是"放大后出现原图没有的纹理/文字"，
  这是超分模型特有的幻觉类缺陷。
- `t2i_v1` / `flux2_klein_t2i_v1`：无参考图，缺陷集中在提示词遵循与形态解剖。

**分层抽样到底解决了什么**（这是选择它的核心理由，用数字说明）：
假设一个 1000 张的批次里，某条工作流只占 1%（10 张）。若按 10% 做**均匀**随机抽
100 张，**一张都没抽到该工作流的概率约为 `0.99^100 ≈ 37%`**。也就是说，
均匀随机有超过三分之一的概率**系统性漏掉一条工作流**——而漏掉的那条一旦正是
新上线、最可能出问题的链，抽检就失去了它的全部意义。分层抽样把这个概率压到 0。

**层内分配（比例分配 + 小层保底）**
- 层的应抽数 = `round(层内张数 / N × 总抽样数)`；
- **保底**：每层至少抽 `min(层内张数, 2)` 张；
- 若各层保底之和 > 总抽样数，则以保底为准（**实际抽样数上浮**），
  并在记录表里记下**实际抽样比**而不是名义 10%；
- 层内用**独立随机源**等概率抽取，不按 idx 顺序取前 k 张
  （顺序取会与出图顺序相关，而批量里同一 SKU 的图是连续生成的 ——
  连着取等于只抽了头几个 SKU）。

**抽样种子必须独立记录。** 抽样随机源用一个**与出图 seed 无关**的种子
（记为 `sample_seed`），并写进记录表。理由：出图 seed 决定图长什么样，
抽样种子决定"看哪些图"，两者混用会让"换了出图 seed 之后抽检结论变化"
分不清是产物变了还是样本变了。

⚠️ **本节的抽样行为目前没有代码实现。** 也就是说 §2.3 的分配算法是按本文
**手工执行**的。这是一个真实的执行风险（手工分层容易漏层），已记入 §7 待办。

## 3. 判废边界：直接引用 `negative.yaml` 的 `severity`

**本 SOP 不发明任何新的判废词汇。** 判废边界就是
`assets/prompt_lib/negative.yaml` 里已经定义好的三档 `severity` ——
该文件的字段注释第 24–26 行原文：

```
#   severity  hit=出现即判废（人工质检直接淘汰）
#             warn=影响观感，可重跑（默认）
#             soft=轻微瑕疵，可接受
```

并且该文件头部（第 17 行）已经把自己的一部分作用域写明为
**「人工质检清单（`severity: hit` 的条目即判废标准）」** —— 本 SOP 只是把这句话
变成可执行的流程，**不是**在给它加新语义。

### 3.1 三档 → 判读处置的映射

| `severity` | 原文含义 | 判读结论 | 是否计入不良 | 处置 |
|---|---|---|---|---|
| `hit` | 出现即判废 | **判废** | ✅ 是 | 该张**必须重跑**（或在批次内被替换），不进交付 |
| `warn` | 影响观感、可重跑 | 记缺陷，**不自动判废** | ❌ 否（按 §3.2 阈值升级） | 按 §3.2 判定"重跑 / 采纳" |
| `soft` | 轻微、可接受 | 记录，判为**良品（带瑕疵）** | ❌ 否 | 直接采纳；仅在累积出现时进缺陷趋势统计 |

**`hit` 是一票否决，不看评分。** 即使一张图在构图、光影上都是满分，
只要命中任一 `hit` 条目即判废 —— 因为 `hit` 里包含合规类（水印 / 文字 /
伪商标 / NSFW / 儿童商业化），这些是**法务风险**而不是质量问题，
不参与"观感好不好"的加权。

### 3.2 `warn` 的升级规则（提案，未校准）

`warn` 默认"可重跑"，但**同一个 `warn` 条目在同一批内密集出现时，它是系统性
失效而不是随机瑕疵**。提案阈值：

- 单批抽检中，**同一 `tag`** 的 `warn` 命中张数 ≥ 抽检张数的 **30%**
  → 该批对应分层**全量复检**（升级为全检），并到缺陷知识库（`docs/sop/defect_kb.md`，
  P8-06 产出）里定位成因与关联参数；
- 单张图命中 **≥3 条不同** `warn` → 判为**待仲裁**（转 §6），不直接采纳。

⚠️ **这两个阈值是提案，不是经验值。** 它们**从未在真实批次上校准过**
（没有真实批次）。首次执行后必须回填点估计并按实际情况调整；调整必须留痕
（改这一节 + 写清依据），不要静默改数。

## 4. 记录表模板

抽检记录**每批一份**，用 CSV / 表格均可，但列必须齐全。下面是列定义
（可直接复制表头）：

### 4.1 表头（逐张一行）

```csv
batch_id,task_id,idx,workflow,model_hash,template_id,width,height,steps,cfg,seed,stratum,hit_ids,warn_ids,verdict,action,judge,judged_at,note
```

| 列 | 类型 | 说明 |
|---|---|---|
| `batch_id` | int | 批次 id |
| `task_id` | int | 子任务 id（抽检单位） |
| `idx` | int | 批次内序号（全局递增，见 `tasks.py:392`） |
| `workflow` | str | 工作流 id，如 `t2i_v1` |
| `model_hash` | str | 底模 hash（`AC-F5` 要求的产物元数据之一） |
| `template_id` | int \| 空 | 无模板留空 |
| `width` / `height` | int | 实际生成分辨率 |
| `steps` / `cfg` / `seed` | num | 实际生效值（**不是请求值**，必须从产物元数据取） |
| `stratum` | str | §2.3 用的分层键值，如 `workflow=t2i_v1` |
| `hit_ids` | str | 命中的 `hit` 条目 id，分号分隔（如 `neg-026;neg-035`）；无则空 |
| `warn_ids` | str | 命中的 `warn` 条目 id，同格式 |
| `verdict` | enum | `良品` / `判废` / `待仲裁` |
| `action` | enum | `采纳` / `重跑` / `退回全检` / `待定` |
| `judge` | str | 判读人标识 |
| `judged_at` | datetime | ISO8601，带时区 |
| `note` | str | 自由备注（**不要在这里写缺陷描述**，缺陷一律用 id 表达） |

### 4.2 批次汇总行（每批一行）

```csv
batch_id,sampled_at,sample_seed,total_images,sampled_count,actual_ratio,strata_covered,good_count,reject_count,pending_arbitration,sampled_good_rate,escalated,note
```

| 列 | 说明 |
|---|---|
| `sample_seed` | §2.3 的抽样独立种子（**必须有**，否则抽样不可复现） |
| `total_images` | 该批总张数 |
| `sampled_count` | 实际抽检张数（可能因保底而上浮） |
| `actual_ratio` | `sampled_count / total_images`，**写实际值而不是名义 10%** |
| `strata_covered` | 覆盖到的层，`workflow:张数` 形式，分号分隔 |
| `good_count` / `reject_count` / `pending_arbitration` | 三档计数，应满足 `good + reject + pending = sampled_count`（**这个恒等式要在填表时自查**） |
| `sampled_good_rate` | **抽检良品率** = `good_count / sampled_count`。⚠️ 见 §4.3 |
| `escalated` | 是否触发了 §3.2 的升级全检（`是/否`） |

### 4.3 ⚠️ 关于「良品率」的措辞纪律

`sampled_good_rate` 是**抽检样本内的比例**，它的正确叫法是
**"抽检良品率"**，不是"这一批的良品率"。

- 它不是全量真值 —— 抽检的定义就是没看全部；
- 也**不要**给它配一个置信区间。在 N<100（全检）时没有抽样误差概念，
  在 N≥100 时 10% 的样本量小到区间宽得没有决策价值。给出一个精确到小数点后
  一位的"良品率 ± 2%"是**伪造精度**。
- 看板（`AC-P3`）上展示时，必须同屏显示 `sampled_count` 与 `actual_ratio`，
  让看的人知道分母是多少。**只有比率、没有分母的良品率，是这个里程碑最容易被
  误读的一个数。**

## 5. 判读作业规范（防疲劳误判）

抽检的判读质量决定整条流程的价值。三条硬性要求：

1. **单次连续判读不超过 50 张。** 超过 50 张后判读人会进入"扫一眼就过"的模式，
   而此时 `hit` 类缺陷（尤其是 `neg-026` 画面中出现文字、`neg-025` 水印）
   恰恰是最容易被一眼带过的。100 张/批的任务必须拆成 ≥2 段，中间有间隔。
2. **同一批的判读人 ≥1 且必须署名。** `judge` 列不允许填"质检"这类角色名 ——
   无法追责的记录在争议仲裁（§6）里是无效证据。
3. **判读时不得只看缩略图。** `neg-001`（低分辨率/模糊）、`neg-002`（失焦）
   在缩略图上不可判；`neg-004`（JPEG 压缩伪影）在缩略图上会被误判为噪点。
   判读必须看**原始尺寸**。这一条同时意味着：判读工作站要有图能原尺寸打开的
   通路（当前取图接口 `GET /assets/{id}/content` 已接入，见 `todolist.md` 的
   P7-05 说明 —— 但**浏览器人工走查从未做过**，见 §7）。

## 6. 争议仲裁流程

**什么叫争议**：两名判读人对**同一张图的同一条目**给出不同结论
（一人判 `hit` 命中、一人判未命中），或对 `verdict` 判定不同。

```
① 争议发生（至少 2 人判读不一致）
        ↓
② 双方各自写下：命中的 negative id + 依据（缺陷出现在画面哪个区域）
   ⚠️ 必须落到 id，不接受"看起来有点怪"
        ↓
③ 由第三人（组长 / 非当事人）独立判读，事先不看前两人的结论
        ↓
④ 三人中 2 人一致 → 以多数结论闭环
        ↓
⑤ 三方各不相同，或第三人无法判定 → 触发「从严原则」
   （判废；该张进重跑，成本可接受，而漏掉一个合规缺陷不可接受）
        ↓
⑥ 无论结论如何，**必须把该条目的边界判例沉淀到缺陷知识库**
   （`docs/sop/defect_kb.md`，P8-06 产出）：
   「什么样的程度算命中 hit」是知识库里最该有、也最容易缺的一段
        ↓
⑦ 闭环时限：**当批交付之前**。不允许把"待仲裁"带进交付记录
```

**为什么从严原则是判废而不是"按多数采纳"**：`hit` 里有 8 条是合规类
（水印 / 文字 / 伪商标 / NSFW / 暴力 / 儿童 / 人体畸变）。这类缺陷的代价是
**非对称**的 —— 重跑一张图的代价是几秒 GPU 或一次人工重出；
一张带伪造品牌标识的图流到客户详情页的代价是法务问题。
在信息不足以判断时，把不确定性推向"多花一点成本"的一侧。

**仲裁的例外（不需要走全流程）**：判读人对"明显不命中"（例如清晰的白底主图
被同事标了 `neg-040` 过曝白底）有异议时，可直接由第三人一眼确认后闭环，
不必让双方写依据。区分标准是**缺陷是否存在本身有争议** vs
**缺陷的程度是否达到 hit 门槛** —— 前者走简流程，后者走完整流程。

## 7. 与评分标准的衔接（P8-02）

评分标准（技术缺陷 / 构图 / 一致性 / 商用可用度，1–5 分，带锚点样例）由
**P8-02 产出 `docs/sop/quality_rubric.md`**。本 SOP **引用**它，不重复定义
评分锚点（重复定义必然导致两处口径漂移）。

### 7.1 职责边界

| | 本 SOP（P8-04） | 评分标准（P8-02） |
|---|---|---|
| 回答 | **抽哪些图** + **什么情况一票否决** | **剩下那些图有多好**（连续量） |
| 输出 | 抽样比、判废清单、`verdict` 三档 | 1–5 分与锚点样例 |
| 单位 | 批次 → 张 | 张 |
| 判据类型 | 布尔（命中 / 未命中） | 序数（分数档） |

### 7.2 执行顺序（**先判废，后打分**）

```
一张图
  → ① 按 §3 查 20 条 hit
       命中 → verdict=判废，**不再打分**（判废是硬门槛，分数不能救回它）
       未命中 → 进入 ②
  → ② 按 quality_rubric 打 1–5 分
       分数低于 rubric 定义的采纳线 → verdict=良品 但记 warn 统计
       分数达标 → verdict=良品
```

⚠️ **不要反过来做**（先打分、分数低的再查 hit）。理由：这会让"高分图免于合规检查"
成为一个可被利用的路径 —— 而分数是主观连续量，判废是不可协商的布尔量。
顺序本身就是一道防线。

### 7.3 接口约定（给 P8-02 的输入）

本 SOP 需要从评分标准得到**两个**值，其余不关心：

1. **采纳线**（分数 ≥ 此值才算可用）—— 决定 §7.2 第 ② 步的 `warn` 归类；
2. **每条 `hit` 条目在 rubric 里的对应锚点样例**（若有）—— 用于仲裁时对齐
   "程度"的判读，减少 §6 的争议发生率。

若 `quality_rubric.md` 尚未产出，本 SOP **可以先行执行**（`hit` 判废不依赖 rubric），
此时第 ② 步暂缺，记录表的 `warn_ids` 照填、`verdict` 只出现"良品/判废"两档。
这个降级态必须在记录表 `note` 里写明，不要假装做了完整流程。

## 8. 本 SOP 的验证方法

流程文档的"通过"不能靠通读一遍就说"没问题"。本 SOP 的验证分三层，
**每层的当前状态都如实标注**：

| 层 | 验证方法 | 现在能不能做 | 状态 |
|---|---|---|---|
| L1 · 结构自洽 | 本文引用的每个 id / 路径 / 行号都能解析、每条 `hit` 都在 `negative.yaml` 里真实存在 | ✅ 能（纯离线） | ✅ **已做**：20 条 `hit` 由 `negative.yaml` 机械导出；计数已用 YAML 解析复核（见 §3.3 的纠正说明） |
| L2 · 桌面演练 | 用 `tests/golden_set/` 的**既有 case**当"假批次"，按 §2 抽一遍、按 §4 填一份记录表，检查每一列都能填、无空列、无"我不知道该填什么" | ⚠️ 部分能 | ⏳ **未做** —— 缺**两样**，都不是"等一会就有"：① 演练要的是**图片**（判读对象），而 `tests/golden_set/reference/` 至今**只有 `.gitkeep`**，参考图素材未入库（P8-01 的 `README.md` §4/§6 已登记）；② golden set 的 **42 个 case 是单张素材**，不是一个 ≥100 张的批次，就算图片到位也需**先构造一份假的批次清单**（且该清单要带 `workflow`/`model_hash`/`idx` 等 §4.1 要求的列）才能演练 |
| L3 · 真实执行 | §0 的四条打勾条件 | ❌ 不能（需 GPU + 真实批量） | ⏳ **未做**，阻塞项见 §9 |

**L2 的诚实说明**：桌面演练**不是**"流程已验证"的等价物 —— 它只能证明
"记录表填得下、规则不矛盾"，不能证明"判读人能在 50 张内不出错"、
更不能证明 10% 这个比例合适。请勿把 L2 通过读成 L3 通过。
