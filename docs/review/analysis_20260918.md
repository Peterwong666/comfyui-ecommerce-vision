## 2. 为什么昨天进度显慢

1. **验证状态语义不清**：`verification` 只有 `gpu_verified` / `static_only` / `pending_gpu` 三个值，无法表达「L4 已真实出图、但缺本工作流口径 baseline」的中间状态。结果 3 条工作流被迫挂在 `pending_gpu`，注册表与 CLI 同时失实。
2. **决策反复被交回用户**：6 个技术取舍反复要求用户确认，而用户反馈是「不理解有什么用，请以项目目标和代码稳定高效为准则决策」。这说明此前的提问方式没有给出推荐方案，增大了沟通成本。
3. **文档/代码漂移**：`engine/validate.py` 对 `verification != gpu_verified` 固定打印「未在 GPU 上真实出图」，但 3 条工作流已真实出图；`37_probe_inpaint_mask_polarity.py` 注释写错 A/B 差异原因。
4. **契约缺口未收口**：`task_max_retries_hard_limit` 是死配置（无消费者）；生成分辨率的 `params` 通道缺口未修；`inpaint_v1` 输入无 alpha 校验。
5. **外部依赖卡手**：autoDL GPU 凭据不在环境/SSH 里，导致所有需 GPU 的任务无法推进。
6. **并行子代理产物需复核**：此前子代理交付的代码曾出现语法错误，必须「真跑 + 真 lint」才采信。

## 6. 关键纪律重申

1. **「渲染路径已验证」≠「工作流可放行」**：`enabled` 仍必须满足 `gpu_verified` + `baseline.measured_at` + `render_path_l4=true`。
2. **不许把 `pending_gpu` 当垃圾桶**：新增 `render_path_l4_passed` 后，`pending_gpu` 只留给「连静态校验都没过」的状态。
3. **inpaint 的 no-op 是安全问题**：普通 JPEG 上传会静默产出同一张图并报成功，比报错更危险；`requires_alpha` 校验已补上。
4. **测试全绿要追问夹具**：本次新增用例覆盖了内存存储替身；真实 MinIO / PG / Redis 行为仍待验证。
5. **做完即更新进度表**：本次改动完成后，`项目进度.md` / `项目进展.md` / `todolist.md` 需同步更新，避免四份文档再次漂移。
