## 1. 埋点要解决什么问题

MRD 定了北极星指标（**周有效交付图片数**）、V1 目标（良品率 ≥80%、成功率 ≥98%）。
但**指标不会自己出现** —— 它必须由埋点事件算出来。

本文档的作用：**定义「埋什么」，使得「想看的指标都能算出来」，且不多埋一个无用事件。**

### 1.1 三条设计原则（承 PRD §7.1）

| # | 原则 | 含义 |
|---|---|---|
| 1 | **北极星可算** | 所有埋点必须能支撑「周有效交付图片数」 |
| 2 | **失败可诊断** | 每个失败必须记录 `错误类型 + 阶段 + 上下文`，否则 PRD §6 的 14 类异常形同虚设 |
| 3 | **不采敏感数据** | 不上传商品图内容；只记元信息（尺寸/格式/数量） |

### 1.2 反面清单（明确不埋）

| 不埋 | 理由 |
|---|---|
| 商品图内容/OCR/图像分析 | 用户隐私与商业机密，且无必要 |
| 用户输入的提示词全文 | 可能含商品名/品牌等敏感信息 → 只记长度与 hash |
| 鼠标轨迹 / 热力图 | V1 无此分析需求，徒增成本 |
| 任何个人身份信息（手机/真实姓名） | 合规最小化原则 |

## 2. 命名与规范

| 项 | 规范 | 示例 |
|---|---|---|
| 事件名 | 小写下划线，`对象_动作` | `task_submitted` |
| 属性名 | 小写下划线 | `batch_size` |
| 公共属性 | 每个事件自动附带 | `user_id` · `session_id` · `ts` · `app_version` · `source` |
| 事件粒度 | 一次用户动作 = 一个事件 | — |
| 时间戳 | 毫秒，服务器时间 | — |
| 幂等 | 关键事件带 `event_id` 去重 | `task_finished` 带 `task_id` |

> **公共属性统一注入**，不在业务代码里重复写。这样规范变化时只改一处。

## 3. 事件总表（12 个核心事件）

### 3.1 用户与准入（M1）

| # | 事件名 | 触发时机 | 属性 | 用途 |
|---|---|---|---|---|
| E01 | `user_register` | 注册成功 | `channel`（来源） | 新增用户数；渠道效果 |
| E02 | `user_login` | 登录成功 | `is_first_today` | 活跃用户（DAU/WAU）；留存计算 |

### 3.2 生成主链路（M2/M3）

| # | 事件名 | 触发时机 | 属性 | 用途 |
|---|---|---|---|---|
| E03 | `image_uploaded` | 上传完成（单张/批量） | `count` · `total_size` · `format` · `mode`(single/batch) | 漏斗第 2 步；上传成功率 |
| E04 | `template_selected` | 用户选中模板 | `template_id` · `category` · `position`(在列表中的位置) | **关键转化点**（旅程 3→4）；模板热度排序 |
| E05 | `param_changed` | 修改关键参数并提交 | `param_name` · `from_visible`(是否在首屏) | 判断该暴露哪些参数（验证画像假设 4） |
| E06 | `task_submitted` | 任务提交成功 | `task_id` · `workflow` · `batch_size` · `mode` · `template_id` · `est_cost` | 漏斗第 3 步；队列压力预测 |

### 3.3 任务执行（M4 · 承 PRD §5 状态机）

| # | 事件名 | 触发时机 | 属性 | 用途 |
|---|---|---|---|---|
| E07 | `task_started` | 状态 → `running` | `task_id` · `wait_seconds`(排队时长) · `gpu_mem_used` | 排队时长分布；显存水位 |
| E08 | `task_retry` | 状态 → `retrying` | `task_id` · `error_type` · `retry_count` · `degrade_action` | **重试率**；OOM 降级有效性（AC-6.1） |
| E09 | `task_finished` | 到达**终态** | `task_id` · `status` · `duration_ms` · `gpu_seconds` · `error_type` · `workflow` · `batch_size` | **成功率 · P95 耗时 · 单张成本 · 良品率分母** |

> **E09 是全项目最重要的埋点**：PRD §7.2 的 6 个指标里有 5 个依赖它。
> 它必须记录**非终态不触发**（否则重试会被算成失败），且带 `error_type`（对齐 PRD §6 的 EX-1~EX-14）。

### 3.4 结果消费（M5）★ 北极星的来源

| # | 事件名 | 触发时机 | 属性 | 用途 |
|---|---|---|---|---|
| E10 | `image_adopted` | 用户标记采纳 | `task_id` · `image_id` · `workflow` · `template_id` | **良品率分子**；质量评估 |
| E11 | `image_downloaded` | 下载（单张/打包） | `task_id` · `count` · `pack`(bool) · `scope`(selected/all) | **北极星分子（有效交付）** |
| E12 | `image_regenerated` | 局部重绘 | `task_id` · `source_image_id` · `region_size` | 结果不满意率；重绘功能价值 |

### 3.5 事件覆盖检查

| PRD 指标 | 依赖事件 | 覆盖 |
|---|---|---|
| 任务成功率 | E09 | ✅ |
| 良品率 | E09 + E10 | ✅ |
| P95 出图耗时 | E09 | ✅ |
| 单张成本 | E09(`gpu_seconds`) | ✅ |
| 北极星（周有效交付） | E11 | ✅ |
| 漏斗转化 | E01~E06 + E10/E11 | ✅ |
| 重试率 | E08 | ✅ |
| 排队时长 | E07 | ✅ |

**结论**：12 个事件足以支撑全部已定义指标，无冗余。✅

## 4. 漏斗定义

```
① 访问落地页
      │ page_view (landing)
      ▼
② 注册/登录 ─────────────── E01 / E02
      │
      ▼
③ 上传素材 ──────────────── E03
      │
      ▼
④ 选择模板 ──────────────── E04   ★ 关键转化点 1
      │                            （旅程 3→4，漏了这里就全漏）
      ▼
⑤ 提交任务 ──────────────── E06
      │
      ▼
⑥ 任务成功 ──────────────── E09(status=succeeded)
      │
      ▼
⑦ 采纳结果 ──────────────── E10   ★ 关键转化点 2
      │                            （主体保真不达标 = 一切归零）
      ▼
⑧ 下载交付 ──────────────── E11   ★ 北极星达成
      │
      ▼
⑨ 再次使用（次日/次周）──── E02/E06  ★ 留存
```

### 4.1 三个关键转化点与观测目的

| 转化点 | 衡量 | 若不达标说明什么 |
|---|---|---|
| ③→④ 上传→选模板 | 模板库可用性 | 模板不够直观/太少/分类混乱 |
| ⑥→⑦ 成功→采纳 | **主体保真度** | 核心卖点不成立，产品需重做 |
| ⑧→⑨ 下载→复用 | 留存价值 | 一次性需求，无复购场景 |

> **⑤→⑥ 的任务成功率若 <98%**，一切上层指标都不可信 —— 因为用户根本没拿到图。

## 5. 指标定义表

> 每个指标都给**精确公式**，避免口径歧义（这是数据可信的前提）。

| 指标 | 公式 | 依赖 | 目标 |
|---|---|---|---|
| 任务成功率 | `succeeded / (succeeded + failed)`<br/>**排除 canceled** | E09 | ≥98% |
| 良品率 | `image_adopted 数 / succeeded 图片数` | E09 + E10 | ≥80% |
| 北极星：周有效交付图片数 | `Σ image_downloaded.count`（周内，按用户去重） | E11 | 增长 |
| P95 出图耗时 | `percentile(duration_ms, 95)` by workflow | E09 | ≤25s（SDXL）<br/>≤60s（FLUX.2 klein） |
| 单张成本 | `Σ gpu_seconds × 单价 / 图片数` | E09 | 可核算 |
| 重试率 | `task_retry 次数 / task 数` | E08 | 越低越好 |
| 自动恢复成功率 | `retry 后 succeeded / retry 总数` | E08+E09 | ≥95% |
| 平均排队时长 | `mean(wait_seconds)` | E07 | 观测项（无目标，取决于负载） |
| 次日留存 | 第 2 天有 E02/E06 的用户 / 第 1 天新用户 | E01/E02/E06 | 观测项 |

### 5.1 口径陷阱（必须写下来）

| 陷阱 | 错误做法 | 正确做法 |
|---|---|---|
| 成功率 | 把用户取消算作失败 | **排除 canceled**（否则用户取消会污染成功率） |
| 成功率 | 重试中就算失败 | 只在**终态**（E09）统计 |
| 良品率 | 生成数做分母 | 用 **succeeded 数**做分母（失败的图用户无法采纳） |
| 良品率 | 用户不标记就当作不采纳 | 需明确告知用户「采纳」的意义，否则分母虚高、良品率虚低 |
| 成本 | 用挂钟时间 | 用 **GPU 秒**（gpu_seconds），避免排队时间计入 |

> **最后一条尤其重要**：单卡串行时，一个任务可能排队 10 分钟、执行 12 秒。
> 若按挂钟时间算成本，会把「排队」这个零成本的时间算成 GPU 成本，结论完全错误。

## 6. 技术实现

### 6.1 埋点位置

| 位置 | 适用事件 | 说明 |
|---|---|---|
| **后端**（主要） | E01~E12 全部 | ① 无法被前端绕过 ② 时间戳可信 ③ 可关联 task_id |
| 前端（辅助） | `page_view` · 曝光类 | 仅用于漏斗入口 |

> **决策：核心事件全部后端埋点。**
> 理由：前端埋点会因为广告拦截、关页面、网络失败而丢数据。
> 而北极星与良品率这类**要写进作品集和 KPI 的指标不能有丢失**。

### 6.2 数据流

```
业务代码 ──▶ 事件收集器（进程内，异步非阻塞）
                      │
                      ├──▶ 日志（JSONL，落数据盘）─▶ 兜底 + 排障
                      │
                      └──▶ 事件表（PostgreSQL）
                                 │
                                 ▼
                          聚合任务（定时）
                                 │
                                 ▼
                          看板 / 报表
```

**为什么双写（日志 + 数据库）**：
数据库是查询用，日志是**兜底与追溯用**。若入库失败（DB 抖动），日志还在。
写入必须是**异步非阻塞**，绝不能因为埋点失败而让出图任务失败。

### 6.3 事件表结构（草案）

```sql
CREATE TABLE events (
  id           BIGSERIAL PRIMARY KEY,
  event_name   TEXT        NOT NULL,
  event_id     TEXT,                    -- 幂等去重
  user_id      BIGINT,
  task_id      BIGINT,                  -- 关联任务（可空）
  session_id   TEXT,
  ts           TIMESTAMPTZ NOT NULL,
  app_version  TEXT,
  props        JSONB       NOT NULL,    -- 差异化属性
  created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_events_name_ts ON events (event_name, ts);
CREATE INDEX idx_events_task    ON events (task_id);
CREATE INDEX idx_events_user_ts ON events (user_id, ts);
```

> 用 JSONB 存差异化属性：12 个事件的属性各不相同，
> 若为每个事件建一张表，会产生 12 张表和 12 套查询逻辑，得不偿失。
> 索引建在 `event_name + ts` 上，满足绝大多数聚合查询。

### 6.4 实现顺序（P10）

| 步骤 | 内容 |
|---|---|
| 1 | 事件表迁移（P2-13 建库时一并做） |
| 2 | 收集器 + 异步写入 |
| 3 | 埋入 E01~E12 |
| 4 | 聚合任务（按天/周） |
| 5 | 看板（良品率 / 成本 / 漏斗） |
| 6 | 埋点自测：每个事件都能被触发并落库 |

## 7. 自测清单（P10 验收用）

| # | 检查项 | 方式 |
|---|---|---|
| 1 | 12 个事件全部能触发并落库 | 手工走一遍全流程，查库 |
| 2 | E09 只在终态触发（重试不重复计） | 构造重试场景，检查事件数 |
| 3 | 埋点失败不影响主流程 | 故意让埋点写入失败，任务应照常成功 |
| 4 | 事件带全公共属性 | 抽查 |
| 5 | 良品率可算出且与人工统计一致 | 交叉验证 |
| 6 | 单张成本用 GPU 秒而非挂钟时间 | 代码审查 |
| 7 | 无敏感数据落库 | 抽查 props 字段 |
| 8 | 看板数据与原始事件一致 | 对账 |
