## 1. 产品概述

### 1.1 一句话定义

> **面向电商商家的 AIGC 商品视觉量产平台**：上传商品图，选择场景模板，
> 批量产出可直接上架的主图 / 场景图 / 细节图，全程可追溯、可复现、成本可核算。

### 1.2 产品定位（引自 MRD §6）

| 支柱 | V1 的落地形态 |
|---|---|
| **保真** | 商品主体不变形、风格不漂 —— 靠参考图锁定 + 控制矩阵 |
| **量产** | 一次几百张、无人值守、崩了能续跑 —— 靠异步队列 + 降级重试 |
| **可度量** | 良品率、耗时、成本都有数 —— 靠 golden set + 看板 + 成本模型 |

### 1.3 目标用户与角色

| 角色 | Persona | V1 权限 | 核心场景 |
|---|---|---|---|
| 普通用户 | ① 小店主/运营 ② 设计师 | 生成、管理自己的素材 | 上传商品图 → 选模板 → 批量出图 → 下载 |
| 管理员 | 项目所有者 | 全部 + 模型/工作流/用户管理 | 上架模板、看成本、处理故障 |

> 品牌方（③）、开发者（④）V1 不作为产品内角色：③ V2 引入，④ 通过 README/API 文档服务。

### 1.4 V1 目标与非目标

**目标（V1 必须达成）**

1. 打通「上传 → 出图 → 下载」完整闭环，非技术用户可自助完成
2. 6 条标准工作流全部上线，每条有 golden set 且一次通过率 ≥80%
3. 单卡 4090 连续 8h 混合压测零崩溃
4. 1000 张批量任务可无人值守完成，失败可续跑
5. 单张成本可核算，良品率可查看

**非目标（V1 明确不做，防范围蔓延）**

❌ 视频生成 ❌ 模型微调 ❌ 对外计费与支付 ❌ 移动端 ❌ 多语言
❌ 多租户/团队协作 ❌ 私有化交付 ❌ LLM 提示词助手

> 完整 Won't 清单见 `requirement_pool.md` §4.7。

## 4. 非功能需求（P1-10）

> 标注 `[实测]` 的为已验证数据，`[目标]` 的为待 P5/P8/P9 验证的承诺值。

### NFR-1 · 性能

| 项 | 指标 | 状态 | 验证方式 |
|---|---|---|---|
| 单张出图（SDXL 1024²/30 步） | **5.00s 中位 / 5.48s P95 / 4.59s 地板** | `[实测]` 2026-09-16 | P2-04，`07_bench_workflow.py` N=12 warmup=1，生产配置 `--highvram` |
| 单张出图（FLUX.2 klein 4B 蒸馏版 1024²/4 步） | **1.83s 中位 / 2.67s P95 / 1.52s 地板** | `[实测]` 2026-09-16 | 同上，cfg=1 |
| 单张 P95（1024²/30 步） | ≤ 25s | `[目标]` | P9-04 压测 |
| 高清修复（x2） | ≤ 90s | `[目标]` | P9-04 |
| 提交响应（POST /prompt） | ≤ 200ms | `[目标]` | 异步设计保证 |
| 页面首屏 | ≤ 2s | `[目标]` | 前端性能测试 |
| 进度推送延迟 | ≤ 1s | `[目标]` | WebSocket |

> **⚠️ 口径说明（2026-09-16 更正）**：09-15 曾记录 SDXL 为 **12.0s**，该值是 ComfyUI 启动后**第一次**出图（含 6.9GB 权重加载），属**冷启动**口径，已被本轮标定推翻并删除。
> 现行口径统一为**稳态**（warmup 1 次后取 N 次样本），因为业务上用户提交的是「第 N 张」（N>1 为常态）。
> 冷启动值本身仍有意义（它决定首次请求的等待体验），当前实测约 **15~20s**，将由 P6 的预热策略覆盖。
>
> **⚠️ 关于「地板」**：本机是**共享宿主机**（128 核、load average ≈ 19，多容器共用磁盘/内存带宽），基准中每约 3 个样本出现一次干扰尖峰，**升级前的基线里同样存在**。
> 因此 median/P95 同时包含外部噪声，**min（地板）才是"稳态能力"的稳健估计**。上表同时列出三者，容量规划请看地板，SLA 承诺请看 P95。
>
> **✅ 已收口**：v0.36.0 升级曾使 SDXL 回落到 7.26s 中位（1.58x）。根因是**新版本默认开启的 dynamic VRAM**（非代码 bug、非注意力后端）。
> 已在 `03_start_comfyui.sh` 固定加 `--highvram` 修复：地板 **4.59s** vs 升级前基线 **4.54s**，**差 1%，回归已消除**（见 `项目进展.md` #17/#18）。

> **量级说明**：4090 24G 单卡决定「单张 10s 级」是物理下限，
> 因此**吞吐必须靠排队而非并发**，这是 §5 状态机与 §6 异常设计的根本原因。

### NFR-2 · 并发与吞吐

| 项 | 指标 | 说明 |
|---|---|---|
| GPU 执行并发 | **1** | ComfyUI 单实例模型常驻显存，强行并发必 OOM |
| 队列容量 | ≥ 10000 任务 | 排队优于崩溃（C12） |
| API 并发 | ≥ 50 QPS | 纯 IO，无 GPU 参与 |
| 批量任务规模 | ≥ 1000 张/任务 | FR-3.6 |
| WebSocket 连接 | ≥ 100 | 进度推送 |

> **关键设计约束**：`执行并发 = 1` 是所有体验设计的隐含前提 ——
> 用户必须能接受「排队」，所以**队列可视化与预计时长（FR-2.6）不是锦上添花，是必需品**。

### NFR-3 · 可用性与稳定性

| 项 | 指标 | 验证 |
|---|---|---|
| 连续压测 | 8h 混合负载**零崩溃** | P9-05 |

## 5. 任务状态机（P1-11）

### 5.1 为什么状态机是 V1 的核心设计

使用者面对的是「提交了 500 张，现在怎么样了」，
而系统内部是「1 个 GPU 串行跑 500 个任务，随时可能 OOM、超时、被取消」。
**状态机是这两者之间的翻译层**。它一旦设计不清，会出现：
任务卡在「运行中」永不结束、取消后仍在跑、失败后无法重试、重试导致重复计费等现象。

### 5.2 状态定义

| 状态 | 语义 | 终态 | 可否取消 |
|---|---|---|---|
| `pending` | 已创建，待调度入队 | 否 | ✅ |
| `queued` | 已入队，等待 GPU | 否 | ✅ |
| `running` | 正在执行 | 否 | ✅（步间隙生效） |
| `retrying` | 因瞬时错误回退等待重试 | 否 | ✅ |
| `succeeded` | 成功产出 | ✅ | — |
| `failed` | 最终失败（重试耗尽） | ✅ | — |
| `canceled` | 用户取消 | ✅ | — |
| `partial` | **批量父任务专用**：部分成功部分失败 | ✅ | — |

> `partial` 是关键设计：批量任务里 500 张成功 3 张失败，
> 不能整体标 `failed`（会让用户误以为全废），也不能标 `succeeded`（掩盖问题）。

### 5.3 批量任务的父子关系

```
BatchTask (父)  ──1:N──▶  Task (子，每个 = 一张图)
     │                          │
     └─ 状态由子任务聚合推导      └─ 维护完整状态机
```

**父任务状态聚合规则**

| 子任务情况 | 父任务状态 |
|---|---|
| 全部 succeeded | `succeeded` |
| 全部 failed | `failed` |
| 部分 succeeded 部分 failed | `partial` |
| 有子任务 pending/queued/running | `running`（进度 = 完成数/总数） |
| 全部 canceled | `canceled` |

### 5.4 状态迁移表

| # | 当前 | 事件 | 目标 | 动作 | 备注 |
|---|---|---|---|---|---|
| T1 | — | 用户提交 | `pending` | 落库，返回 task_id | — |
| T2 | `pending` | 调度器取任务 | `queued` | 入 Redis 队列 | 校验配额 |
| T3 | `pending` | 用户取消 | `canceled` | — | — |
| T4 | `queued` | 用户取消 | `canceled` | 出队 | — |
| T5 | `queued` | Worker 取任务 | `running` | 记录开始时间、显存 | — |
| T6 | `running` | 执行成功 | `succeeded` | 保存产物 + 元数据 | — |
| T7 | `running` | 瞬时错误（OOM/超时/连接） | `retrying` | 记录错误，退避等待 | 计入 retry_count |
| T8 | `retrying` | 退避结束且 retry < 上限 | `queued` | 重新入队 | 默认上限 3 |
| T9 | `retrying` | retry ≥ 上限 | `failed` | 记录最终错误 | — |
| T10 | `running` | 用户取消 | `canceled` | 步间隙中断，清理显存 | 不在采样中途硬杀 |
| T11 | `running` | 致命错误（非法参数/模型缺失） | `failed` | **不重试** | 重试无意义 |
| T12 | 子任务状态变更 | — | 重算父状态 | 更新进度 | §5.3 规则 |
| T13 | `failed`/`partial` | 用户点重试 | `pending` | 仅重试失败子任务 | FR-3.5 |
| T14 | `running` | Worker 崩溃 | `queued` | 启动时扫描僵尸任务 | NFR-3 优雅重启 |

> **T7 vs T11 的区分是设计要点**：OOM 值得重试（降级后可能成功），
> 非法参数不值得重试（重试一万次还是错）。混淆两者会导致「队列被必然失败的任务堵死」。

### 5.5 状态机图

```
                    ┌──────────┐
     用户提交 ──────▶│ pending  │
                    └────┬─────┘
              调度入队    │    └──────用户取消──────▶ canceled
                    ┌────▼─────┐                     ▲
                    │  queued  │───用户取消───────────┘
                    └────┬─────┘
              Worker 取  │
                    ┌────▼─────┐
                    │ running  │───用户取消──────────▶ canceled
                    └──┬────┬──┘
         成功           │    │  瞬时错误(OOM/超时)
              ┌─────────▼┐  ┌▼──────────┐
              │succeeded │  │ retrying  │
              └──────────┘  └─────┬─────┘
                                  │
                    retry<3 ┌─────┴─────┐ retry>=3 / 致命错误
                            │           │
                       ┌────▼───┐  ┌────▼────┐
                       │ queued │  │ failed  │
                       └────────┘  └────┬────┘
                                        │ 用户重试
                                   ┌────▼─────┐
                                   │ pending  │
                                   └──────────┘
```

### 5.6 状态机的验收标准

| AC | 标准 | 验证方式 |
|---|---|---|
| AC-5.1 | 任一任务不会永久停留非终态（超时保护） | 压测 + 僵尸扫描 |
| AC-5.2 | 取消在 ≤1 个采样步内生效 | 集成测试 |
| AC-5.3 | 重试不产生重复产物 | 产物去重校验 |
| AC-5.4 | 父任务状态与子任务聚合一致 | 单测覆盖全部聚合分支 |
| AC-5.5 | Worker 崩溃后任务自动恢复（T14） | 杀进程演练 |

## 6. 异常与边界处理（P1-12）

### 6.1 异常处理表

| ID | 场景 | 触发条件 | 系统行为 | 用户可见 | 可重试 |
|---|---|---|---|---|---|
| **EX-1** | **显存不足（OOM）** | CUDA OOM | ① 降分辨率/步数（降级策略）② 清显存缓存 ③ 转 `retrying` | 「显存不足，已自动降低精度重试」 | ✅ 自动 |
| **EX-2** | 单张超时 | 超过阈值（默认 300s） | 中断该张 → `retrying` | 「出图超时，正在重试」 | ✅ 自动 |
| **EX-3** | 非法参数 | 参数越界/类型错 | 提交时前端拦截；后端二次校验 → `failed`（T11，不重试） | 「参数不合法：步数需在 1-100」 | ❌ |
| **EX-4** | 磁盘满 | 剩余空间 < 阈值（如 5G） | 停止接收新任务，告警管理员；运行中任务尽量完成 | 「存储空间不足，请联系管理员」 | ✅ 手动 |
| **EX-5** | 并发超限 | 队列深度 > 上限 | 拒绝提交 → `pending` 保留，提示排队 | 「当前排队 N 个，预计等待 X 分钟」 | ✅ 手动 |
| **EX-6** | 重复提交 | 同用户同参数短时间重复（幂等键） | 返回**已有** task_id，不新建 | 「该任务已提交」 | — |
| **EX-7** | Worker 崩溃 | 进程异常退出 | 启动时扫描 `running` 且心跳超时的任务 → `queued`（T14） | 「任务已自动恢复」 | ✅ 自动 |
| **EX-8** | ComfyUI 无响应 | 健康检查连续失败 | 重启 ComfyUI 实例，未完成任务回队 | 「推理引擎重启中」 | ✅ 自动 |
| **EX-9** | 模型文件缺失/损坏 | hash 校验不符 | 任务 `failed`（T11），告警 | 「模型不可用，请联系管理员」 | ❌ |
| **EX-10** | 上传非法文件 | 类型/大小/解码失败 | 拒绝上传，明确原因 | 「仅支持 JPG/PNG/WebP，≤20MB」 | — |
| **EX-11** | 单张生成失败但批量其余正常 | 子任务异常 | 该子任务 `failed`，父任务继续 → `partial` | 详情页标红该张 | ✅ 单张 |
| **EX-12** | 配额耗尽 | 用户额度用完 | 拒绝提交新任务 | 「额度已用完」 | — |
| **EX-13** | 产物保存失败 | 存储写入异常 | 保留 ComfyUI 临时产物，重试保存；仍失败则 `failed` | 「结果保存失败，正在重试」 | ✅ 自动 |
| **EX-14** | 用户中途关页面 | — | 任务不受影响，继续执行 | 重新进入可在任务中心看到 | — |

## 7. 数据与埋点（概要）

> 完整事件表见 `tracking_plan.md`（P1-20）。本节只定义**埋点原则**与**关键指标**，确保 PRD 与埋点方案自洽。

### 7.1 埋点原则

1. **北极星可算**：所有埋点必须能支撑「周有效交付图片数」（= 生成且被下载/采纳）。
2. **失败可诊断**：每个失败任务必须记录 `错误类型 + 阶段 + 上下文`，否则 EX 表形同虚设。
3. **不采敏感数据**：用户上传的商品图**不做内容级埋点**，只记元信息（尺寸/格式/数量）。
4. **漏斗可还原**：关键路径（上传→选模板→生成→采纳→下载）每一步都要有事件。

### 7.2 关键指标与埋点映射

| 指标 | 定义 | 依赖事件 |
|---|---|---|
| 任务成功率 | succeeded / (succeeded+failed) | `task_finished` |
| 良品率 | 采纳数 / 生成数 | `task_finished` + `image_adopted` |
| 平均出图耗时 | mean(duration) by workflow | `task_finished` |
| 单张成本 | Σgpu_seconds × 单价 / 张数 | `task_finished(gpu_seconds)` |
| 漏斗转化 | 各步人数比 | `page_view` + 各行为事件 |
| 重试率 | retrying 次数 / 任务数 | `task_retry` |
