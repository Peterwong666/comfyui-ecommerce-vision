# ADR-008 V1 范围收缩：风格迁移顺延 V2 · 内容安全只留接口与人工抽检 · 不引入图像重依赖

- 日期：2026-09-17
- 状态：已定

## 背景

V1 的验收口径此前写作「6 条标准工作流全部上线且可跑通」（`docs/prd/PRD_v1.md:609` 的 AC-F1）。
逐条核实代码与资产后发现，**这个口径在 V1 不可能达成**：注册表里第 6 条 `style_transfer_v1`
只是一个**占位条目、没有对应定义文件**，且它的三条实现路径全部断在「权重在磁盘上不存在」上
（`workflows/registry.yaml:1263-1275`）。

同时另有两项与「V1 到底交付什么」直接相关的范围问题，长期处于**既没说做、也没说为什么不做**的模糊状态：

- `FR-9.4`（NSFW 过滤开关与策略，**Must**，`docs/prd/PRD_v1.md:252`）—— 文档里只写「V1 未实现」，没写口径；
- `P8-03` 自动质检（NSFW / 模糊度 / 过曝欠曝 / 畸形 / 尺寸 / 留白，`todolist.md:410`）—— 同理。

三者都不是「技术做不出来」，而是**在 V1 的时间盒与项目铁律下不该做**。
本 ADR 一次性把三条裁定写死，目的是：① 让 AC-F1 有一个**可达成**的口径；
② 防止后续会话把这三件事反复重新讨论，或「顺手」实现成一个**看起来能用、实际没有依据的空壳**
（本项目最忌讳的一类失败，见 `backend/app/services/content_safety.py:417-421` 的记载）。

> ⚠️ 本 ADR 引用的行号与事实均在 **2026-09-17** 逐条重新核实（读文件 / grep / 解析 `object_info` 快照），
> 核实不了的一律标注「未核实」，不照抄他处结论。

## 决策（三条）

| # | 裁定 | 一句话 |
|---|---|---|
| 1 | `style_transfer_v1`（P3-07）**顺延 V2**，V1 **不下载**它的三类权重 | V1 上线 **5 条**工作流；`AC-F1` 口径随之修正 |
| 2 | V1 **不做 NSFW 视觉检测**，只做**输入侧文本过滤 + 人工抽检**；V2 走「构建期下载离线小分类器」 | `NullNsfwDetector` 保持**永返 `unknown`、永不返 `safe`** |
| 3 | V1 **不引入 numpy / Pillow 等图像重依赖**；将来做时用 **optional extra**，不进必装依赖 | `P8-03` 顺延并拆成 `P8-03a` / `P8-03b` |

## 裁定 1：`style_transfer_v1`（P3-07）顺延 V2，V1 不下载它的三类权重

### 背景

`workflows/registry.yaml:1263` 注册了 `style_transfer_v1`，但 `workflows/` 目录下**只有 5 个定义文件**
（`t2i_v1.json` / `flux2_klein_t2i_v1.json` / `i2i_v1.json` / `inpaint_v1.json` / `upscale_v1.json`），
**没有 `style_transfer_v1.json`** —— 它被刻意放在注册表的 `planned:` 段而不是 `workflows:` 段
（`registry.yaml:1255-1262` 解释了为什么「指向不存在文件的条目」不能进正式段）。

阻塞原因写在 `blocked_by`（`registry.yaml:1266`）：**三类权重目录枚举全空**，三条实现路径全断：

| # | 缺什么 | 证据（`registry.yaml:1269-1271`，基于 `/object_info` 快照逐项核实于 2026-09-16） |
|---|---|---|
| ① | **IP-Adapter 本体权重** | `IPAdapterModelLoader.ipadapter_file` 枚举为空 |
| ② | **CLIP-Vision 编码器权重** | `CLIPVisionLoader.clip_name` 枚举为空（IP-Adapter 的**硬前置**） |
| ③ | **LoRA 权重** | `LoraLoader.lora_name` 枚举为空 |

锁定路径的另外两条：`engine/model_registry.yaml:296-306` 的 `ipadapter_sdxl` / `ipadapter_plus_sdxl`
属于 `planned:` 段（**尚未下载**，`commercial_ok: unknown`）；同文件 `:335` 的 LoRA 条目标题本身就是
「`<待选：质感/光影/材质/风格 LoRA>`」。

### 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| ① **下载三类权重并过许可审查** | 功能完整，FR-6.2 的 6 条口径保住 | CLIP-Vision 编码器许可**未核实**（`docs/sop/license_matrix.md:171` 标 `⚠️ unknown`；§7 待核实清单 #8 状态「**未开始**」，`license_matrix.md:259`）；解锁它等于把 P4 控制体系的整条链（P4-03 / P4-09）一起拉进 V1，而 P4 目前 **0/10**（`todolist.md:311-320` 十项逐条核对**无一打勾**） | ❌ |
| ② **顺延 V2** | 时间盒留给已能闭环的 5 条工作流与平台层；等 P4 的权责一起解 | AC-F1 口径要改、V1 少一条工作流 | ✅ **选定** |
| ③ **用别的手段近似**（纯提示词风格描述 / `img2img` + 风格提示词） | 零权重成本，看起来「有风格迁移」 | **已被现有决策堵死**：`registry.yaml:1274-1275` 明确写「**不做「img2img + 风格提示词」的降级版** —— 那不是真正的风格迁移（无参考图驱动），命名为 style_transfer 会造成「功能名不副实」—— **宁可缺一条，不要一条名不副实的**」 | ❌ |

### 决定

**顺延 V2。V1 不下载 IP-Adapter / CLIP-Vision / LoRA 三类权重中的任何一类。**

### 理由

1. **CLIP-Vision 编码器的许可未核实，而项目铁律是「未知即不用」。**
   `docs/sop/license_matrix.md:16`：「**未知即不用** —— 找不到明确许可证的模型一律不用，找替代品；不存侥幸心理。」
   而 `license_matrix.md:171` 把「IP-Adapter 的 CLIP Vision 编码器」的许可状态明确标为 `⚠️ unknown`，
   并特别提醒「**单独登记，不要与 IP-Adapter 本体混为一条**」—— 非 FaceID 变体正是依赖它，
   所以这一条是 base / plus 能否商用的**关键路径项**。「未知」在这里不是"可能没问题"，是**不能开始**。
2. **IP-Adapter 是 P4「控制体系」的正主，而 P4 在 V1 里根本没有时间盒了。**
   `todolist.md:313`（P4-03 IP-Adapter 接入）与 `todolist.md:319`（P4-09 一致性方案用 IP-Adapter）
   都还是空白；`engine/model_registry.yaml:27` 亦记载「P4-03（IP-Adapter）未启动」。
   V1 的时间盒已经消耗在 P2（基础设施）/ P3（工作流）/ P6（平台封装）/ P7（前端）上，
   把控制体系整条链拉进 V1 会挤掉已经能闭环的部分。
3. **电商商品图的核心场景，用现有 5 条已能覆盖。**
   主图 / 场景图 / 细节图这三类 V1 首发场景，靠 `t2i` + `i2i` + `inpaint` + `upscale` + `klein`
   已经能跑通完整链路；「风格迁移」相对它们是**增量能力而非刚需**（`docs/adr/0001-delivery-form-and-scope.md:30`
   把电商视觉定为 V1，理由正是"范式固定、最容易标准化"）。
4. **「近似实现」这条捷径不是没想过，而是已经被否掉。** 见上表方案 ③。

### 代价

- **V1 只有 5 条可用工作流**，`AC-F1`（原「6 条全部上线」）口径必须改 ——
  已在 `docs/prd/PRD_v1.md` §8.1 修正为「**5 条 V1 上线 + 1 条顺延 V2**」，并同步 `todolist.md` 的
  §2.3 范围表、P3-07 行与 P3 阶段结果（口径为「5 条可用 + 1 条顺延」）。
- V2 启动时这三类权重仍要**从零走一遍许可审查 → 下载 → 接入 → 评测**，成本不会因为顺延而消失，只是推后。
- 「风格迁移」这条能力在 V1 对外描述里**不得出现为已交付**。

## 裁定 2：V1 不做 NSFW 的视觉检测，只做输入侧文本过滤 + 人工抽检

### 背景

`FR-9.4` 的原文是「NSFW 过滤开关与策略」，优先级 **Must**（`docs/prd/PRD_v1.md:252`）。
「策略与开关」这半边已经落地（P6-13 输入侧文本过滤，`backend/app/services/content_safety.py`），
但**视觉检测**这半边 V1 不做。已查实的事实：

| # | 事实 | 证据 |
|---|---|---|
| 1 | ComfyUI 的 **2530 个节点类里没有任何安全 / NSFW 分类节点** | 解析 `deploy/schemas/object_info.v0.36.0.json`，`len(d) == 2530` |
| 2 | ⚠️ **陷阱 A**：`easy prompt` 节点里那个叫 `nsfw` 的入参**语义相反** | 其定义是 `"🔞Select the nsfw add to the text"`，枚举值为 `nude` / `breast` / … —— 它是**帮用户把 NSFW 词加进提示词**的下拉，**不是过滤器** |
| 3 | ⚠️ **陷阱 B**：`WanVideoBlockList` 与内容安全**无关** | 其定义是「Comma separated list of blocks to apply block swap to」，输入 `blocks` 是字符串、输出 `block_list` 是 `INT` —— 那是 WanVideo 的**层号列表**，名字里的 "BlockList" 指的是 transformer block |
| 4 | 模型注册表里**只有 6 个已下载模型，全是出图用底模 / VAE / 文本编码器** | `engine/model_registry.yaml` 的 `models:` 段共 6 条（`:61` `sd_xl_base_1.0` checkpoint / `:95` `flux-2-klein-4b` unet / `:131` `flux2-vae` vae / `:161` `sdxl_vae_fp16fix` vae / `:191` `qwen_3_4b` text_encoder / `:222` `qwen_3_4b_fp4_flux2` text_encoder），与该文件 `:15` / `:23` 的「6 个文件已实测核对」一致 —— **没有任何分类器** |
| 5 | 后端**零图像依赖**（无 numpy / Pillow / torch） | `backend/pyproject.toml:6-37` 的依赖集逐项核对 |
| 6 | 项目有成文的「避免重依赖」纪律 | `backend/app/services/image_probe.py:10`：「**都是拿几十行确定的代码换掉一个重依赖**」 |

### 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| ① **云内容安全 API** | 检测能力强、零本地依赖、无需许可审查 | **与项目的两条硬约束直接冲突**：<br>· `docs/flow/system_flow.md:235-236` 明确要求「模型下载**只在构建期发生，运行时不访问外网**」——这是私有化部署（E9）的前提；<br>· `docs/prd/tracking_plan.md:23` 的隐私原则 3「**不采敏感数据**——**不上传商品图内容**；只记元信息」（`:29` 亦把「商品图内容 / OCR / 图像分析」列为"用户隐私与商业机密，且无必要"） | ❌ |
| ② **离线小分类器**（构建期下载 HF 系权重） | 符合「构建期下载、运行时不联网」约束；本地推理 | **必须先过许可审查** —— 铁律「未知即不用」（`license_matrix.md:16`）同样适用于分类器权重 | ✅ **但推到 V2** |
| ③ **只做输入侧文本过滤 + 人工抽检** | 零新增依赖、零许可风险、可立即交付 | **拦不住违规画面** | ✅ **V1 选定** |

### 决定

1. **V1 只做输入侧文本过滤**（**已交付**：`backend/app/services/content_safety.py`，
   422 + `code=CONTENT_BLOCKED`，词表 `backend/app/data/content_blocklist.json`）
   **+ 人工抽检**（SOP 已交付：`docs/sop/quality_sampling_sop.md`，P8-04）。
2. **V2 走方案 ②（离线小分类器）**，但引入前必须：
   ① **先核实权重许可**；② 登记进 `engine/model_registry.yaml`；③ 再替换 `NullNsfwDetector`。

### 理由

1. **云 API 与两条硬约束冲突**（见上表方案 ①）。私有化部署要求运行时不出网；
   而把商品图上传到第三方，等于把客户的商业机密送出边界 —— 这两条都不是可以「权衡」的偏好，是前提。
2. **离线小分类器符合「构建期下载」约束**，但**必须先过许可审查**。
   「构建期下载」解决的是"能不能离线跑"，**不解决"能不能商用"** —— 后者要逐个核 LICENSE 原文。
3. **人工抽检不是我方发明，而是项目自己的对策。**
   `docs/sop/license_matrix.md:238`（§6 输出内容合规）在讨论「生成图中出现他人商标 / 卡通 IP」时写明：
   「反向词包里已有 `neg-027`（伪造品牌标识），但反向词在 cfg=1 链路无效 → **必须靠人工核查**」。
   同理，`content_safety.py:413` 也指出未实现的替代手段就是「`license_matrix.md` §6 指出的**人工核查**」。

### 代价（如实写）

- **违规画面系统当前拦不住。** 输入侧词表只能覆盖**可枚举的文本**（`content_safety.py:20-21`），
  绕写（拆字 / 拼音 / 谐音 / 插引号）与**图片内容本身**都覆盖不到。
- 该风险已登记：`项目进度.md:19` 的风险清单里就有「**R16 内容安全只有输入侧文本过滤、无视觉检测**」。
- 对外**不得声称「NSFW 过滤已上线」** —— 开关打开不会让任何图片被检测
  （`backend/app/core/config.py:108-109` 已就此写了显式警告）。

### 补充裁定：`NullNsfwDetector` 的语义**不得**被放宽

`backend/app/services/content_safety.py:407-426` 的 `NullNsfwDetector` **永返 `NsfwStatus.UNKNOWN`、永不返 `SAFE`**，
且 `NsfwStatus` 是三态（`safe` / `unsafe` / `unknown`，`content_safety.py:386-391`）。

**这是刻意设计，不是遗漏**：一个返回「安全」的空检测器**比没有检测器更糟** ——
它会让下游（调用方、看板、报表）把「未检测」当成「已检测且通过」，从而**让风险隐形**。
（同类教训：契约里冻结的埋点事件名 `image_adopted` 曾长期零触发；`AssetOut` 的注释写着"取图走受控接口"
而那个接口当时并不存在 —— 见 `content_safety.py:417-420`。）

> 🔒 **在 V2 引入真检测器之前，禁止把 `NullNsfwDetector.detect()` 改成返回 `safe`。**
> 若要放宽，必须先有一个真实工作的检测器。

## 裁定 3：V1 不引入 numpy / Pillow 等图像重依赖

### 背景

`P8-03 自动质检` 列了六项：**NSFW、模糊度、过曝欠曝、畸形（手/文字）、尺寸、留白**（`todolist.md:410`）。
已查实：

- 后端 **零图像依赖**（`backend/pyproject.toml:6-37`：fastapi / uvicorn / pydantic / sqlalchemy / alembic /
  psycopg / celery / redis / minio / httpx / websockets / pyjwt / bcrypt，**没有 numpy / Pillow / torch**）；
- `backend/app/services/image_probe.py` 的 docstring **把纪律写成了文**（`:10`）：
  「都是为了"不引入重依赖"而手写头部解析。**都是拿几十行确定的代码换掉一个重依赖。**」

按「要不要模型」把六项拆开（**这是本裁定的分类依据**）：

| 类别 | 指标 | 是否可离线算 | 说明 |
|---|---|---|---|
| **尺寸** | 尺寸 | ✅ **现在就能算，且零依赖** | 已由 `image_probe.probe()` 从图片头解析（PNG / JPEG / WebP，`image_probe.py:59-154`） |
| **像素级统计** | 留白 / 过曝欠曝 / 模糊 | ⚠️ **不需要模型，但需要完整像素解码** | 必须引入图像库（Pillow / numpy 之类）才能解码全图；纯头部解析做不到 |
| **需要模型** | NSFW / 手部与文字畸形 | ❌ 不能 | 必须要一个模型（见裁定 2） |

### 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| ① 加进 `backend/` 的**必装依赖** | 用起来最省事 | 让**服务**背一份**只在质检工具链**用的依赖（体积 MB 级；具体数字未核实）；且给"运行时"引入了本不需要的重量 | ❌ |
| ② **optional extra**（按需安装） | **用的人付代价**；服务的依赖集保持干净；不违反「构建期下载」约束 | 使用时多一步安装 | ✅ **将来做时采用** |
| ③ **V1 不做** | 零成本；不产出"看着有、其实没标定"的空壳 | `P8-03` 顺延 | ✅ **V1 选定** |

### 决定

**V1 不做 P8-03；将来做时用方案 ②（optional extra），不放进服务的必装依赖。**

并把 `P8-03` 拆成两项，使"哪一半卡在哪"不再含糊：

- **`P8-03a`**：**离线粗指标**（尺寸 / 留白 / 过曝欠曝 / 模糊）—— 不需要模型，
  但**待有真实产物**（阈值标定必须用真实图）。
- **`P8-03b`**：**NSFW 与畸形（手 / 文字）** —— **V2 需模型**，与裁定 2 同一条路。

### 理由

1. **阈值标定必须用真实图，而 V1 目前一张真实评测图都没有。**
   golden set 的 `expected` **全为 `null`**、`expected_status` 全为 `pending_gpu`
   （`todolist.md:408`）。在没有真实产物的前提下做质检，只能得到一个**「阈值未标定」的空壳** ——
   它输出数字、看起来在工作，但没有任何依据说明阈值该是多少。
2. **放进必装依赖会让「服务」背一份只在「质检工具链」用的依赖。**
   服务的运行时依赖集是它自己的接口面；把工具链需求混进去，等于让部署者为不用的功能付体积与升级成本。
3. **optional extra 让「用的人付代价」**，且因为它只在构建/工具链阶段安装，**不违反「运行时不访问外网」**的约束
   （`system_flow.md:235-236`）。

### 代价

- **`P8-03` 顺延**，V1 的质量体系只有「人工抽检」这一条（P8-04 的 SOP 本身**也从未执行过一次**，
  `todolist.md:411`）；P8 阶段 DoD「良品率有数、有看板、可下钻」**远未达成**。
- 拆成 `08a` / `08b` 后**不改变 P8 的阶段任务数**（与 `P8-08a` / `08b` 同一口径）。

| 2 · 不做 NSFW 视觉检测 | **违规画面当前拦不住**；不得声称"NSFW 过滤已上线" | **R16**（`项目进度.md:19`） |
| 3 · 不引图像重依赖 | P8-03 顺延；质量体系只剩人工抽检 | P8 阶段 DoD 远未达成（`todolist.md:423`） |

> ⚠️ 三条裁定的共同点：**都是在"做不了"与"做出一个空壳"之间选了前者。**
> 本项目对"空壳"的定义是——**有产出物、有输出、但没有任何依据支撑它的结论**。
> 这也是为什么本 ADR 要求每条裁定都写明「代价」，而不是只写「决定」。
